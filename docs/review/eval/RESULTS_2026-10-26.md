## 7. Findings the numbers expose (for the paper's discussion; none changed in code tonight)
1. **Keyword alone is weak (0.697)**: full-text search needs every word to match; Luna's multi-word queries often match nothing: 11 of 38 questions found no gold item by keyword (q09, q14, q15, q17, q18, q20, q21, q22, q25, q26, q27).
2. **Fusion equals semantic-only** on this set: the keyword branch did not change any top-10.
3. **The cross-encoder + effort step lowered MRR (0.899 vs 0.987).** Measured cause (q28, q30): the cross-encoder scores are about 0.000-0.003 for every candidate, so `0.8*ce + 0.2*effort` is decided by the effort term, and a mail the owner had opened (effort 0.048) outranks the right item (0.027). Rank 1 became rank 2 in q27-q30 and rank 3 in q31. Likely (basis: the scores above, not tested further): the ms-marco model saturates on these short, specific questions.
4. **Time-anchored question q21** ("after the Brightwave interview email"): Luna put the phrase into `query` and left `anchor_item` empty, so recall was 0.20 (0.40 over all items shown). Time questions with a start date only (q22 "today", q25 "16 October") lose items because the filter has no end date.
5. **Stage-1 classification**: all 6 new mails were labelled `structural` = personal group, because their Gmail category is Personal, including an offer letter and a course syllabus. Not yet checked against the decided design.
6. `python -m rse.retrieval_engine` run from the command line crashes in the semantic branch on a cold start (huggingface_hub import inside the worker thread); warming the models on the main thread fixes it. The running backend loads the models in the enrichment worker first, so it is likely unaffected (not tested through HTTP).
